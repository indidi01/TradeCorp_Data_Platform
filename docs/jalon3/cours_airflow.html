🌀 Cours Airflow

Apache Airflow

Orchestrer, planifier et surveiller des pipelines de données — sans intervention humaine.

Le problème de départ

Votre pipeline TradeCorp fonctionne. Mais aujourd'hui, pour le faire tourner, il faut qu'un humain ouvre un terminal et tape quatre commandes dans le bon ordre :

python  src/fetch_exchange_rates.py
spark-submit src/reader.py
spark-submit src/transformer.py
spark-submit src/writer.py

Chaque nuit à 6h. Sans se tromper d'ordre. Sans oublier. Et si la deuxième commande plante, il faut s'en rendre compte, comprendre pourquoi, et relancer à la main.

Pourquoi pas un simple cron ?

cron (Linux) ou le Planificateur de tâches (Windows) savent lancer une commande à heure fixe. Mais ils ne savent pas :

  • gérer des dépendances entre étapes (« lance B seulement si A a réussi »)
  • réessayer automatiquement une étape qui a échoué
  • garder un historique lisible de ce qui a tourné, quand, et avec quel résultat
  • vous montrer visuellement où ça bloque
Un orchestrateur fait exactement cela : il exécute des étapes dans un ordre défini, gère les échecs, conserve l'historique, et expose une interface pour tout surveiller. Airflow est l'orchestrateur open-source de référence en Data Engineering.

Un peu d'histoire

Créé chez Airbnb en 2014 par Maxime Beauchemin pour orchestrer leurs pipelines internes, ouvert en open-source en 2015, projet Apache de premier niveau depuis 2019. Aujourd'hui utilisé par des milliers d'entreprises.

Les composants d'Airflow

Airflow n'est pas un seul programme, mais plusieurs qui coopèrent :

🌐 Webserver

L'interface web (port 8080). Vous y voyez vos DAGs, l'état de chaque exécution, les logs. Vous pouvez déclencher ou relancer des tâches à la main.

⏱️ Scheduler

Le chef d'orchestre. Il lit vos DAGs en permanence, décide quelles tâches doivent être lancées et quand, et les envoie à l'executor. C'est lui qui fait tourner le pipeline, pas le webserver.

🗄️ Base de métadonnées

Une base PostgreSQL où Airflow stocke tout : la liste des DAGs, l'historique de chaque exécution, le statut de chaque tâche, les utilisateurs, les connexions. Sans elle, pas de mémoire.

⚙️ Executor

La façon dont les tâches sont réellement exécutées. Nous utilisons LocalExecutor : les tâches tournent en parallèle sur la même machine.

Les executors

ExecutorFonctionnementUsage
SequentialExecutorUne tâche à la fois, avec SQLiteTests uniquement
LocalExecutorPlusieurs tâches en parallèle, sur une machine, avec PostgreSQLNotre cas — développement et petits déploiements
CeleryExecutorTâches distribuées sur plusieurs machines (workers)Production à grande échelle

Pourquoi Docker ?

Airflow a besoin de Python, d'une base PostgreSQL, d'un scheduler et d'un webserver qui tournent en même temps. L'installer nativement sur Windows est notoirement pénible. Avec Docker Compose, tout démarre en une commande — exactement la logique du Jalon 1.

services:
  postgres:     # métadonnées Airflow
  airflow:      # webserver + scheduler
  spark:        # votre pipeline (déjà là)

Le DAG — cœur d'Airflow

DAG = Directed Acyclic Graph, graphe orienté acyclique. Traduction : un ensemble de tâches reliées par des flèches, sans boucle. C'est simplement le dessin de votre pipeline.

fetch_exchange_ratesappel API
→
readerlecture ADLS
→
transformerSpark
→
writerécriture ADLS
  • Directed (orienté) : les flèches ont un sens, reader vient après fetch_exchange_rates
  • Acyclic (sans cycle) : impossible de revenir en arrière — sinon le pipeline ne finirait jamais

Anatomie d'un DAG en Python

Un DAG est un simple fichier Python déposé dans le dossier dags/. Airflow le lit automatiquement.

from airflow import DAG
from datetime import datetime, timedelta

default_args = {
    "owner": "tradecorp",
    "retries": 1,                          # réessayer 1 fois en cas d'échec
    "retry_delay": timedelta(minutes=5),   # attendre 5 min avant de réessayer
}

with DAG(
    dag_id="tradecorp_etl_pipeline",       # nom unique du DAG
    default_args=default_args,
    start_date=datetime(2024, 1, 1),       # date à partir de laquelle il "existe"
    schedule_interval="0 6 * * *",         # cron : tous les jours à 6h
    catchup=False,                          # ne pas rattraper le passé
    tags=["tradecorp", "etl"],
) as dag:

    # ... les tâches ici ...

    t0 >> t1 >> t2 >> t3                   # l'ordre d'exécution
ParamètreRôle
dag_idIdentifiant unique, affiché dans l'interface
start_dateDate de "naissance" du DAG. Aucune exécution avant.
schedule_intervalFréquence d'exécution (expression cron ou raccourci @daily)
catchupSi True, Airflow rejoue toutes les exécutions manquées depuis start_date. Presque toujours False.
retries / retry_delayPolitique de nouvelle tentative en cas d'échec
>>Définit la dépendance : a >> b = « b attend que a réussisse »
Piège classique : start_date=datetime(2024,1,1) avec catchup=True déclencherait des centaines d'exécutions pour rattraper tous les jours depuis 2024. Mettez toujours catchup=False sauf besoin explicite.

Les opérateurs — ce que fait une tâche

Un Operator est un modèle de tâche. Une Task est un opérateur instancié dans un DAG avec un task_id. Il existe des dizaines d'opérateurs ; trois couvrent la grande majorité des besoins.

BashOperator — exécuter une commande shell

from airflow.operators.bash import BashOperator

t = BashOperator(
    task_id="dire_bonjour",
    bash_command="echo 'Bonjour TradeCorp' && date",
)

La commande s'exécute dans le conteneur Airflow. Utile pour des scripts shell, des copies de fichiers, des appels à des outils en ligne de commande installés dans ce conteneur.

PythonOperator — exécuter une fonction Python

from airflow.operators.python import PythonOperator

def calculer():
    total = 2 + 2
    print(f"Résultat : {total}")
    return total

t = PythonOperator(
    task_id="calculer",
    python_callable=calculer,
)

La fonction s'exécute dans le conteneur Airflow, avec les bibliothèques Python qui y sont installées. Parfait pour un appel API, une petite transformation, une vérification.

DockerOperator — lancer un conteneur

from airflow.providers.docker.operators.docker import DockerOperator

t = DockerOperator(
    task_id="transformer",
    image="tradecorp-spark",                          # l'image à lancer
    command="spark-submit /home/jovyan/src/transformer.py",
    docker_url="unix://var/run/docker.sock",          # accès au Docker de l'hôte
    network_mode="tradecorp_default",                 # même réseau que les autres services
    auto_remove=True,                                 # supprimer le conteneur à la fin
    mount_tmp_dir=False,
    mounts=MOUNTS,                                    # volumes src/, data/, .env
)

Airflow demande à Docker de créer un conteneur éphémère à partir d'une image, d'y exécuter une commande, puis de le détruire. La commande s'exécute donc dans ce conteneur-là, pas dans Airflow.

Pourquoi le DockerOperator dans notre projet ?
Spark et Java sont installés dans le conteneur tradecorp_spark, pas dans le conteneur Airflow. Un BashOperator avec spark-submit répondrait command not found. Un PythonOperator avec import pyspark planterait sur JAVA_GATEWAY_EXITED. Seul le DockerOperator peut lancer le pipeline dans l'environnement où Spark existe.

Comparatif

OpérateurS'exécute où ?Bon pourLimite
BashOperatorConteneur AirflowCommandes shell simplesNe voit que ce qui est installé dans Airflow
PythonOperatorConteneur AirflowLogique Python légère, appels APIIdem — pas de Spark ici
DockerOperatorUn nouveau conteneur, depuis une imageTout ce qui a besoin d'un environnement spécifique (Spark, Java…)Plus de configuration (socket, réseau, volumes)

Le scheduler — quand ça tourne

Le scheduler vérifie en boucle : « y a-t-il un DAG dont l'heure est venue ? ». Si oui, il crée un DAG run (une exécution) et lance les tâches dans l'ordre des dépendances.

Lire une expression cron

┌───────── minute (0-59)
│ ┌─────── heure (0-23)
│ │ ┌───── jour du mois (1-31)
│ │ │ ┌─── mois (1-12)
│ │ │ │ ┌─ jour de la semaine (0-6, dimanche=0)
│ │ │ │ │
0 6 * * *      → tous les jours à 06:00
0 */2 * * *    → toutes les 2 heures
30 8 * * 1-5   → 08:30 du lundi au vendredi
0 0 1 * *      → le 1er de chaque mois à minuit

Raccourcis acceptés : @hourly, @daily, @weekly, @monthly. Pour vérifier une expression : crontab.guru.

Les états d'une tâche

ÉtatCouleurSignification
queuedgrisEn attente d'un slot d'exécution
runningvert clairEn cours
successvertTerminée sans erreur
failedrougeÉchec — après épuisement des retries
up_for_retryorangeÉchec, nouvelle tentative programmée
upstream_failedorange foncéPas lancée car une tâche précédente a échoué
Relancer une tâche : dans l'interface, cliquer sur la tâche → Clear. Airflow la remet en queued et la relance, ainsi que toutes celles qui en dépendent.

Les sensors — attendre qu'une condition soit vraie

Un Sensor est un opérateur spécial qui ne fait rien… sauf attendre. Il vérifie une condition à intervalle régulier et ne passe en success que lorsqu'elle est remplie. Les tâches suivantes attendent avec lui.

FileSensor — attendre l'arrivée d'un fichier

from airflow.sensors.filesystem import FileSensor

attendre_fichier = FileSensor(
    task_id="attendre_go",
    filepath="/opt/airflow/data/trigger/go.txt",   # le fichier attendu
    poke_interval=30,       # vérifier toutes les 30 secondes
    timeout=60 * 60,        # abandonner après 1 heure
    mode="poke",
)

attendre_fichier >> t0 >> t1 >> t2 >> t3
ParamètreRôle
filepathChemin du fichier attendu, vu depuis le conteneur Airflow
poke_intervalFréquence de vérification (secondes)
timeoutDurée max d'attente avant de passer en failed
modepoke : garde un slot occupé en attendant. reschedule : libère le slot entre deux vérifications (mieux pour de longues attentes)

Cas d'usage TradeCorp : le script MySQL legacy dépose les CSV chaque nuit à une heure variable. Plutôt que de lancer le pipeline à 6h « en espérant » que les fichiers soient là, un sensor attend leur arrivée réelle puis déclenche la suite.

Attention : un sensor en mode poke sans timeout peut bloquer un slot indéfiniment. Toujours définir un timeout.

Le DAG TradeCorp — ce qu'il doit faire

Voici ce que votre DAG doit accomplir à la fin du Jalon 3. Rien de nouveau côté transformation : il ne fait qu'appeler vos scripts existants, dans le bon ordre, chaque nuit. À vous de l'écrire.

fetch_exchange_ratespython
→
readerspark-submit
→
transformerspark-submit
→
writerspark-submit

Ce que le fichier doit contenir

  • Les imports nécessaires : DAG, DockerOperator, Mount, datetime/timedelta
  • Les default_args (owner, retries, retry_delay)
  • Le chemin du projet sur la machine hôte et la liste des volumes à monter (src/, data/, .env)
  • Le DAG lui-même : identifiant, date de début, planning quotidien à 6h, catchup désactivé, tags
  • Quatre tâches DockerOperator — même image, mêmes paramètres, seule la commande change
  • L'ordre d'exécution
Conseil : les quatre tâches partagent 8 paramètres identiques et ne diffèrent que par leur task_id et leur commande. Une petite fonction qui fabrique une tâche à partir de ces deux éléments vous évitera de copier-coller quatre blocs quasi identiques — c'est exactement l'esprit de la programmation modulaire du Jalon 2.

Les paramètres du DockerOperator, expliqués

docker_url="unix://var/run/docker.sock"Airflow parle au démon Docker de la machine hôte via ce socket (monté dans le docker-compose)

Les pièges rencontrés — et leurs solutions

spark-submit: command not found → vous utilisez un BashOperator : Spark n'est pas dans le conteneur Airflow. Passer au DockerOperator.
can't open file '/home/jovyan/src/reader.py' → les mounts sont manquants ou mal configurés dans la tâche.
bind source path does not exist: /mnt/c/... → sur Docker Desktop Windows, le chemin hôte s'écrit //c/Users/..., pas /mnt/c/... ni C:\....
bind source path does not exist: /tmp/airflowtmp... → ajouter mount_tmp_dir=False.
Port 8080 déjà utilisé → un autre service (Jenkins, par exemple) l'occupe. Changer le port côté hôte ("8081:8080") ou arrêter l'autre service.
Le DAG n'apparaît pas dans l'interface → vérifier que le fichier est bien dans le dossier dags/ monté dans le conteneur Airflow (docker exec tradecorp_airflow ls /opt/airflow/dags/) et qu'il n'a pas d'erreur de syntaxe Python.

Le service Airflow dans docker-compose.yml

airflow:
  build:
    context: .
    dockerfile: Dockerfile.airflow      # FROM apache/airflow + requirements.txt
  container_name: tradecorp_airflow
  depends_on: [postgres]
  environment:
    AIRFLOW__CORE__EXECUTOR: LocalExecutor
    AIRFLOW__DATABASE__SQL_ALCHEMY_CONN: postgresql+psycopg2://tradecorp:tradecorp@postgres/tradecorp
    AIRFLOW__CORE__LOAD_EXAMPLES: "false"
  ports: ["8080:8080"]
  volumes:
    - ./dags:/opt/airflow/dags
    - ./src:/opt/airflow/src
    - ./.env:/opt/airflow/.env
    - /var/run/docker.sock:/var/run/docker.sock   # indispensable au DockerOperator
  command: bash -c "airflow db migrate && airflow users create --username admin --password admin --firstname Admin --lastname Admin --role Admin --email admin@admin.com && airflow webserver & airflow scheduler"

Le requirements.txt doit contenir apache-airflow-providers-docker pour que le DockerOperator soit disponible.

Ce qu'il faut retenir

1

Airflow orchestre, il ne transforme pas. Il lance vos scripts dans le bon ordre et surveille ; la logique métier reste dans src/. Si votre pipeline ne marche pas à la main avec spark-submit, Airflow ne le réparera pas.

2

Un DAG = un fichier Python dans dags/. Airflow le détecte tout seul. Tâches + dépendances (>>) + planning (schedule_interval).

3

Le scheduler décide, le webserver montre. Si l'interface est accessible mais que rien ne se lance, c'est le scheduler qu'il faut regarder.

4

Un opérateur s'exécute quelque part de précis. Bash et Python : dans le conteneur Airflow. Docker : dans un conteneur neuf créé à partir d'une image. Demandez-vous toujours « où ce code va-t-il tourner, et ce dont il a besoin y est-il installé ? »

5

catchup=False par défaut. Sinon Airflow rejoue tout le passé depuis start_date.

6

Les échecs sont normaux, c'est leur gestion qui compte. retries, retry_delay, lecture des logs, Clear pour relancer. Un pipeline qui échoue proprement vaut mieux qu'un pipeline qui réussit silencieusement avec de mauvaises données.

7

L'idempotence est votre amie. Relancer une tâche deux fois doit donner le même résultat — pas deux fois plus de fichiers dans le Data Lake. C'est la correction faite dans writer.py (suppression avant upload).

8

Un sensor attend, il ne travaille pas. Toujours lui donner un timeout.
